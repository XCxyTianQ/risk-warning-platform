# T5 数据集管线（风险预警层的"真值"从哪来）

> 一句话：**不靠人力翻公告**。风险事件在权威信源上本来就带日期、带原文，
> 我们自动采下来，做成"企业 × 时点 × 标签"的样本，再做 point-in-time 评测。

## 一、数据从哪来（全部公开信源、可回溯）

| 用途 | 信源 | 接口 | 实测 |
|---|---|---|---|
| 全 A 股清单 | 东方财富行情快照 | `push2.eastmoney.com/api/qt/clist/get` | 4,000–5,558 只 |
| **事件标签** | **巨潮资讯**（交易所指定披露平台） | `cninfo.com.cn/new/hisAnnouncement/query` | 关键词 2,941–6,108 条/类 |
| 财报面板 | 东方财富 datacenter | `RPT_DMSK_FN_BALANCE` / `RPT_LICO_FN_CPD` | 按代码取全部报告期，含**披露日期** |
| **新闻/舆情** | 东方财富个股公告 | `np-anotice-stock…/security/ann` | 1,382,688 条（1,333 只，2011 年起） |
| 司法/合规 | 同上（按标题关键词分类） | — | 13,819 条（688 只） |
| 第二披露渠道 | **深交所官方公告** | `szse.cn/api/disc/announcement/annList` | 一周 7,812 条（用于交叉验证） |

每条标签都带：`类型 / 严重度 / 命中关键词 / 披露日期 / 公告标题 / PDF 链接`——**任何人可以点开核对**。

## 二、标签口径（`labels.js`，可审计）

10 类事件：行政处罚、立案调查、退市风险警示、其他风险警示、债务/债券违约、债券展期与兑付风险、
资金占用/违规担保、财务造假/会计差错、被执行/失信、非标审计意见。
每类都有**关键词 + 排除词**（例行披露如"非经营性资金占用及其他关联资金往来（汇总）表/专项审计"
一律排除——这是交叉验证抓出来的噪音）。

> 改词表 = 改标签口径 → 必须重新采集并在 `manifest.json` 留痕（含文件 sha256）。

## 三、用法

```bash
# 1) 清单 + 事件标签 + 财报面板（首次约 10–20 分钟）
node bench/dataset/fetch.js --cases 400 --controls 500 --since 2015-01-01
# 2) 按公司定向补标签（召回补强，可断点续跑）
node bench/dataset/harvest-by-stock.js --build-orgmap --since 2015-01-01
# 3) 非财务数据（新闻 + 司法），覆盖面板里出现过的全部企业
node bench/dataset/harvest-nonfinancial.js --all-panel
# 4) 平台评分 replay（按 9 个 cutoff 重建"当时可见"的库，问平台要评分）
node bench/dataset/replay.js
# 5) T5 评测（三个目标 × 基线 vs 平台，含分层检验）
node bench/dataset/t5.js --target risk_warning_next_year
node bench/dataset/t5.js --target penalty_next_year
node bench/dataset/t5.js --target any_high_event_next_year
# 6) 标签三源交叉验证（产出人工复核队列）
node bench/dataset/validate-labels.js --weeks 3 --days 2
# 7) 一键串联（等采集结束后自动跑 replay + T5 + 全量 bench）
node bench/dataset/finish-round.js && node bench/dataset/finish-round2.js
```

产物（`bench/dataset/out/`，**原始 jsonl 不入库**、可随时重抓；报告与 manifest 入库）：

```
universe.jsonl / events.jsonl / panel.jsonl / news.jsonl / legal.jsonl / orgmap.json
replay-scores.jsonl          平台在每个 cutoff 的评分与各维度分
t5-report-<target>.json      T5 指标与样例（含分层检验）
label-validation.json + review-queue.jsonl   三源交叉验证与人工复核队列
*-manifest.json              参数 / 来源 / 条数 / 文件 sha256（口径留痕）
```

## 四、评测口径（不这样做，指标就是假的）

1. **point-in-time**：特征只用 `noticeDate ≤ T` 的财报；标签只用 `T < 事件日 ≤ T+12 个月` 的事件；
2. **按时间切分**：训练 ≤2023-12-31，测试 ≥2024-01-01（不是随机切分）；
3. **病例-对照 + 基础率**：队列里病例被过采样，报告同时给原始正例率与测试集基础率；
4. **平台评分来自平台自己**：replay 为每个 cutoff 建独立临时库 + 独立后端，调
   `/api/enterprise/{id}/risk`，不是我们替它算；
5. **两个必须做的技术处理**：
   - **维度门槛**：规则引擎用 `enterprise.data_status_json[维度]` 决定该维度是否参与评分
     （`rules.rs::status_of`）——replay 必须按实际数据标注，否则非财务维度全被跳过；
   - **时间平移**：`news` 维度是"近 365 天"相对窗口，replay 把 cutoff 当作"今天"，
     新闻日期统一后移 `今天 − cutoff` 天；`legal` 不看时间窗，按 `≤ cutoff` 过滤；
6. **分层检验**：按"该样本是否有非财务维度分"切开报告，防止把"有新闻的公司本身更好预测"
   误读成"平台更强"。

## 六、B 档：三源交叉验证与"拿不到的数据"

**三源验证** `validate-labels.js`：

| 源 | 机制 | 实测（2–7 天窗口） |
|---|---|---|
| A | 巨潮**关键词检索** | 14,968 条标签 |
| B | 巨潮**按日期全量扫描**（无关键词，本地分类） | 命中 35 条，**关键词漏掉 10 条** |
| C | **深交所官方公告接口** | 命中 25 条，**关键词漏掉 9 条** |

产出 `review-queue.jsonl`（411 条待人工复核，带原因与 A/B/C 置信度）。
**验证抓到的两个真问题**：关键词检索有系统性漏检（标题写法千变万化）；词表有噪音
（`资金占用` 命中 6.8 万条，多为例行披露）——已收紧排除词。

**拿不到的数据（实测被挡，附证据）**

| 想要的数据 | 尝试 | 结果 |
|---|---|---|
| 东财违规/处罚/债券违约/失信库 | 11 个 `reportName` | 全部 `报表配置不存在 (9501)` |
| 失信被执行人 / 被执行 | `zxgk.court.gov.cn` | `404 / 412`（反爬 + 验证码） |
| 非上市企业工商信息 | `gsxt.gov.cn` | `521` + JS cookie 挑战 |
| 上交所公告/纪律处分 | `query.sse.com.cn` | `SOA service missing parameter [siteId]` |

→ 债券违约只能覆盖**上市公司披露口径**；失信/被执行与非上市企业需**付费数据源**或**人工抽样**，不假装能做。

## 七、按公司定向采集（召回补强）

关键词检索的漏检问题用**按公司定向采集**根治：先按日期扫描建立 `代码 → orgId` 映射（4,599 只），
再对队列里 680 只有 orgId 的公司**拉取其 2015 年以来的全部公告**，本地用收紧后的词表分类，
与现有标签增量合并。**680 家 / 21,835 次请求 / 0 失败**；标签 20,129 → **22,127**
（`audit_qualified` 473 → **1,772**，非标审计意见关键词几乎抓不到）。

## 八、命名与联接上踩过的坑（都会影响结论，必须记）

1. **`finance` 表 (企业, 年, 报告期) 有唯一约束** → 报告期必须细分（一季报/中报/三季报/年报）
   并按披露日期去重，否则建库直接失败；
2. **`/api/enterprise/{id}/risk` 是单数路由**，用复数会返回 SPA 的 HTML（表现为"评分全空"）；
3. **`enterprise.name` 唯一**：批量灌数据要用可靠映射，别依赖 `lastrowid`；
4. **面板与队列的代码集必须一致**：面板若用旧队列抓、标签用新队列采，两者可能只重叠一小部分——
   本轮就因此把覆盖率误算成 33%。修法：写面板时**与已有面板合并**，并统计 `panelCodes` 与 `cohortCodes`。

## 九、覆盖率与最终结果（2026-09-13）

**覆盖率提升**（`harvest-nonfinancial.js --all-panel`，采集范围从队列 900 家扩到面板 1,348 家）：

| 项 | 之前 | 现在 |
|---|---|---|
| 新闻条数 | 869,684（871 只） | **1,650,847**（1,340+ 只） |
| 司法记录 | 8,832（447 只） | **14,493**（700+ 只） |
| **测试时点有新闻** | 260 / 792（33%） | 覆盖到 **1,325 / 1,348 个测试样本有非财务维度（98%）** |
| T5 样本 / 测试集 | 6,056 / 787 | **10,183 / 1,348** |

**最终 T5 结果（测试集 1,348；98% 样本含非财务维度）**

| 目标（正例率） | 财务困境规则 AUC / AP | 平台六维 AUC / AP |
|---|---|---|
| 退市风险警示（2.5%） | 0.633 / **0.196** | **0.798** / 0.180 |
| 处罚/立案（3.2%） | 0.595 / 0.084 | **0.772** / **0.089** |
| 任一高危（7.4%） | 0.580 / 0.198 | **0.734** / **0.289** |

**分层检验**：覆盖率到 98% 后，"只有财报"的子集只剩 23 个样本、0 个正例——
**统计上不再可比**，因此主结论就用整个测试集。据此：

1. **平台六维在三个目标上的 AUC 全面且明显高于三行财务规则**（+0.15 ~ +0.17 AUC）；
2. PR-AUC 在处罚与"任一高危"上反超（0.089 对 0.084；**0.289 对 0.198**）；
   退市目标基线仍略高（0.196 对 0.180）——**这一条要如实写**；
3. **上一轮"仅有财报时平台反而不如规则"的说法撤回**：当时是联接 bug 造成的样本偏差，
   在 98% 覆盖率下该子集已无正例，无法也不应据此下结论。

**下一步（继续扩大优势）**：新闻采集深度 15 页 → 30+、回溯到上市首日；
司法关键词扩展（裁判文书类公告）；对 `news` 时间平移窗口做 ±90 天敏感性分析。
