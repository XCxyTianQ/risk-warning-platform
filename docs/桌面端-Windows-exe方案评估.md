# Windows 桌面端（exe）工程难度评估

> 评估对象：把现有「Vue 前端 + FastAPI 后端 + SQLite」打包成 Windows 桌面应用。
> 评估基准：本机实测（2026-09-08）+ 现有代码结构。

## 1. 现状盘点（决定工期的硬事实）

| 项 | 实测值 | 对打包的影响 |
|---|---|---|
| 前端构建产物 `web/dist` | **1.31 MB** | 极小，随包分发无压力 |
| 后端依赖 `site-packages` | **237.7 MB**（pandas 61.8 / numpy 31.3 / sqlalchemy 18.1 / akshare 9.0 / lxml 8.9） | exe 体积主要来源，预计安装包 **180~260 MB** |
| Node | v24.16.0 ✅ | 前端构建就绪 |
| Rust / cargo | **未安装** | Tauri 需额外装工具链（~1.5 GB + 学习成本） |
| WebView2 运行时 | **已安装 152.0.4191.66** | 本机可直接跑；终端用户 Win10+ 多数自带，缺失可随包引导安装 |
| 前端路由 | `createWebHistory`（history 模式） | 必须由后端托管并做 SPA fallback（file:// 直接打开会 404） |
| 前端接口地址 | 相对路径 `/api`（无硬编码后端 host） | ✅ 生产构建可被同源后端直接托管 |
| 后端端口 | 固定 8001（8000 被其他进程占用） | 桌面端必须**动态选空闲端口** |
| 数据路径 | 仓库相对 `data/platform.db` | 桌面端必须迁到 `%APPDATA%` |
| 密钥存储 | `server/.env` 明文 | 桌面端建议改用 **Windows 凭据管理器 / DPAPI** |

结论：**技术栈完全可打包**，主要工程量在"运行时环境适配 + 打包调优"，不在功能开发。

## 2. 方案对比

| 方案 | 桌面壳 | 产物体积 | 额外学习成本 | 工程量 | 适合场景 |
|---|---|---|---|---|---|
| **A. pywebview + 内嵌 FastAPI**（推荐） | 系统 WebView2 | 180~260 MB | 几乎为零（纯 Python） | **≈ 9 人天**（P0 可跑 5 天） | 竞赛演示、内网部署、快速交付 |
| B. Tauri + Python sidecar | 系统 WebView2 | **40~60 MB** | Rust 工具链 + 语法（2~3 天） | ≈ 10~13 人天 | 追求小体积/自动更新/长期产品化 |
| C. Electron | 自带 Chromium | 250~350 MB | 中（主/渲染进程模型） | ≈ 9~11 人天 | 生态最成熟、需要复杂桌面能力 |
| D. 单 exe 起服务 + 默认浏览器 | 无 | 180~260 MB | 无 | **2~3 人天** | 仅内部使用、不要求独立窗口 |

**推荐 A**：改造量最小、不需要新语言、WebView2 本机已具备；先用 A 把"能装能用"跑通，后续若确实需要自动更新或更小体积再迁 Tauri（后端代码几乎不用动）。

## 3. 工程量分解（方案 A，按现有代码逐项）

| # | 工作项 | 说明 | 人天 |
|---|---|---|---|
| 1 | 前端静态托管 | FastAPI `StaticFiles` 挂载 `web/dist` + SPA fallback（非 `/api` 路径回 `index.html`）；Vite `base: './'` | 0.5 |
| 2 | 运行时适配 | 动态选空闲端口；单实例锁；关闭窗口时优雅停服；日志落盘 | 0.5 |
| 3 | 数据路径迁移 | DB / 缓存 / 导出目录改到 `%APPDATA%\RiskWarningPlatform\`；首次运行初始化 + 迁移脚本 | 0.5 |
| 4 | 密钥安全存储 | `.env` → Windows 凭据管理器（`keyring`）或 DPAPI 加密；设置面板改为读写凭据 | 1.0 |
| 5 | 桌面壳 | 窗口尺寸/图标/标题、菜单（文件/帮助/打开日志）、托盘（最小化/退出）、外链用系统浏览器打开、启动失败错误页 | 1.5 |
| 6 | PyInstaller 打包 | `onedir` 优先（首启快）；处理 akshare/pandas/lxml 隐藏导入与数据文件、`uvicorn` 动态导入、前端资源收集 | 2.0 |
| 7 | 打包后回归 | AkShare 联网、LLM 调用、SQLite 路径、WebView2 渲染、中文路径、无网络降级 | 1.5 |
| 8 | 安装包 | Inno Setup：开始菜单/桌面快捷方式、卸载、静默安装、WebView2 缺失时引导 | 1.0 |
| 9 | CI 出包 | GitHub Actions `windows-latest`：构建前端 → PyInstaller → Inno Setup → Release 附件 | 0.5 |
| | **合计** | P0（1~5 + 6 的最小版）约 **5 人天**；完整可分发版 **≈ 9 人天** | **9.0** |

## 4. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| PyInstaller 打包 akshare/pandas 缺模块、首启报错 | **高** | 先做最小可运行打包（跳过 akshare）验证链路，再逐步加隐藏导入；用 `--onedir` + 显式 `collect_all` |
| 产物 180~260 MB、首启 3~8 秒 | 中高 | onedir 代替 onefile；把 akshare 改为**可选依赖**（不用自动采集时不影响启动） |
| 无代码签名 → SmartScreen 警告 | 中 | 演示用说明文档；正式发布购买证书（¥1~3k/年） |
| 杀软误报（PyInstaller 常见） | 中 | 提交白名单、避免 UPX 压缩、提供哈希校验 |
| WebView2 缺失（老系统） | 低 | 安装包内置 Microsoft 引导程序（~2 MB） |
| AkShare 依赖外网 | 中 | 无网络时降级为本地样例数据 + 明确提示（现有"数据状态门控"已支持） |
| 端口冲突/多开 | 低 | 动态端口 + 单实例互斥体 |
| 数据迁移损坏 | 低 | 首次运行复制而非移动；保留备份 |

## 5. 建议路线

```
P0（5 人天）  单 exe 可跑：静态托管 + 动态端口 + 数据路径 + 桌面壳 + 最小打包
P1（4 人天）  可分发：凭据存储 + Inno Setup 安装包 + CI 自动出包 + 回归测试
P2（可选）    产品化：自动更新（GitHub Release 检查）、崩溃日志上报、可选迁移 Tauri 减小体积
```

## 6. 与移动端的衔接（供后续评估）

后端已是纯 HTTP + SSE，前端是响应式 Web，后续做 Android/iOS 有两条路：
- **Capacitor** 套壳（复用现有前端，改动小，约 3~5 人天）
- **uni-app/小程序**（需要重写前端，约 15+ 人天）

桌面端做完后，移动端主要是"打包 + 权限 + 离线缓存"的工作，风险低于桌面端。

## 7. 结论

- **可行性**：高。现有代码无需重构，主要是运行时环境适配 + 打包调优。
- **难度**：中等偏下（方案 A）。最大不确定性在 PyInstaller 打包 akshare/pandas，建议第一步就做"最小可运行打包"验证。
- **工期**：P0 约 5 人天可交付"能装能用"的 exe；完整可分发版约 9 人天。
- **建议**：先做方案 A 的 P0；是否上安装包/自动更新/签名，取决于是否需要给评委或外部用户分发。

## 8. 补充：面向「队内分发测试」的选型建议

测试场景的评价标准与产品发布不同：

| 维度 | 权重（队内测试） | 说明 |
|---|---|---|
| 分发成本 | 高 | 每轮改动都要重发安装包的话，200 MB 走微信/网盘很累 |
| 迭代速度 | 高 | 测试期改动频繁，需要"改完 1 分钟就能让人看到" |
| 环境一致性 | 高 | 队友机器不装 Python、不同依赖版本是最大故障源 |
| 调试便利 | 高 | 出问题时能否立刻看到后端日志 |
| 体积/签名/更新 | 低 | 内部使用，SmartScreen 警告可接受 |
| 长期产品化 | 低 | 现阶段不追求 |

### 三条路线对比（按测试场景重排）

| 路线 | 工期 | 迭代速度 | 环境一致性 | 调试 | 结论 |
|---|---|---|---|---|---|
| **① 局域网集中部署**（一台机器跑后端+前端，队友浏览器访问 `http://<IP>:8001`） | **0.5 天** | 改完刷新即生效 | 完全一致（只有一个环境） | 你能直接看日志 | **功能测试首选** |
| **② 方案 D**（单 exe 起服务 + 自动开浏览器） | 2~3 天 | 每次改动要重发 exe | 好（自带运行时） | 本机可看日志 | 折中 |
| **③ 方案 A**（pywebview 独立窗口 exe） | 5~9 天 | 每次改动要重发 exe | 好 | 队友侧日志难取 | **需要"真桌面应用"体验时选它** |
| ④ Tauri / Electron | 10+ 天 | 更慢 | 好 | 复杂 | 现阶段不推荐 |

### 关键判断

- **如果测试目标是"业务功能是否好用"**（数据准不准、Agent 回答对不对、预警闭环顺不顺）→
  **①局域网集中部署**最优：共用一份 API Key（省钱）、数据统一（所有人的测试记录都在一个库里）、改完即生效、你随时能看日志。后续要演示 exe 时再打包。
- **如果测试目标是"最终交付形态"**（评委/用户要双击 exe、断网也能开、演示桌面体验）→
  **③方案 A**：队友双击即用，不用装 Python；代价是每轮重发 ~200 MB，建议用 **onedir + zip** 而不是 onefile（首启快、不易被杀软误报）。
- **②方案 D** 是二者的折中：工期只有 A 的一半，队友同样是"双击 exe"，只是界面在浏览器里——对功能测试完全够用。

### 落地建议（若选 exe 路线）

1. 打包成 **onedir 目录 + `启动.bat`**，压 zip 分发（比 onefile 快得多，也少杀软误报）；
2. 程序内保留 **设置面板填 API Key**（已实现），避免把 Key 写进分发文件；
3. 加 **便携模式**：数据写 exe 同级 `data/` 目录，队友卸载时直接删文件夹；
4. 版本号显示在标题栏 + 状态栏，便于确认队友测的是哪一版；
5. 集中部署路线可作为"快速验证通道"长期保留（不冲突，后端代码完全复用）。
