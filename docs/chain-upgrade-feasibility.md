# 平台链路能力提升：可行性研究

> 问题：让**平台中的 deepseek**（即口径 B，走平台 HTTP API + 25 工具 + 编排）也做基准能力测试，
> 用 **Prompt / Skill / MCP 工程**能否把成绩拉起来？
>
> 结论：**可行，且成本很低（预计 ¥10 以内、2 小时内可出结论）**。根因已定位到一个具体的产品缺陷，而不是模型的锅。
> 本文只做可行性判断与实验设计，不含动工。

---

## 一、先把差距量准（不量准就无法判断可行性）

此前报告里的"口径 A 88.3% → 口径 B 69.5%（−18.8pp）"有**两个口径错误**，必须先修：

| 问题 | 实情 |
|---|---|
| 样本不同 | 口径 A 是 300 题抽样（实际 298 有效），口径 B 只跑了 **60 题**——两者直接相减无意义 |
| 判分疑似失真 | 口径 B 有 11/60 输出成 `**ABDE**` 这类 markdown 形式，疑似判分器读不懂 |

**修正后的真实差距**（`tools/compare-chain-vs-direct.js` 产物 `out/chain-vs-direct.json`）：

```
同一批 60 题（已验证 B ⊂ A，题号 60/60 交叠）：
  口径 A（直连模型，harness 提示词）  53/60 = 88.33%
  口径 B（平台链路，原判）            41/60 = 68.33%
  口径 B（归一化判分，剥掉 markdown）  41/60 = 68.33%   ← 与归一化前完全一致
  → 真实差距 20.0pp，其中"判分口径"贡献 0.0pp
```

**所以：不是判分问题，是真差距。** 判分器本来就认得 `**ABDE**`，是我最初写的正则不认。

## 二、根因假设（有旁证，可被实验证伪）

| 旁证 | 数值 | 含义 |
|---|---|---|
| 平台工具调用次数 | **0/60** | 这些是金融考试选择题，**没有任何工具能回答它** |
| 平台链路耗时 | 2,799 ms/题 | 比口径 A（4,311 ms/题）**更快** → 输出/推理更短 |
| 错答形态 | 16 题错 + 3 题空 | 错答里大量是"分析性文字 + 选项"，不是裸字母 |

**主假设：系统提示词与任务类型冲突。** 平台 `SYSTEM_PROMPT`（`backend/src/agent/prompt.rs`）明确写着：

> 你的能力来自工具调用，**不要凭记忆回答数据问题**；所有企业数据、评分、风险事实都必须通过工具获取；……

而 CFLUE 题目（如"根据反假货币知识，下列哪些属于…"）**恰恰是一道"凭知识作答"的题，且无工具可用**。
模型于是被推进一个矛盾：被要求必须调工具 → 没有工具能帮上 → 于是给出含糊的分析式回答，而不是干脆的选项。

**次假设：工具 schema 与技能发现机制的上下文开销。** 25 个工具 + `list_skills`/`load_skill` 的描述常驻系统提示，
可能稀释模型对"直接作答"的倾向。

> 这已经不是"模型不行"，而是**产品缺陷**：真实用户问一句"什么是假币"，平台也会去调企业数据工具。

## 三、平台今天已经给了三个杠杆（全部运行时可改，无需重编译）

代码证据：

| 杠杆 | 载体 | 证据 |
|---|---|---|
| **Prompt** | `preset.prompt_extra` 追加到系统提示后 | `agent/runner.rs:162-163`：`format!("{SYSTEM_PROMPT}\n\n[当前预设：{}]\n{}", p.name, p.prompt_extra)` |
| **Tools** | `preset.tools` 白名单过滤 | `agent/tools.rs`：`retain_whitelist()`，且 `list_skills`/`load_skill` 永远保留 |
| **Skill** | `skill` 表（`name` / `description` / **`content`**）+ `list_skills` / `load_skill` 工具；`preset.skills` 决定装哪些 | `db/schema.rs`、`services/presets.rs` |
| **MCP** | 外部工具以 `mcp_` 前缀注入，描述前缀 `[MCP:服务名]` | `api/mcp.rs`、`services/mcp.rs`、`prompt.rs:24-25` |
| **Model** | `preset.model_override` 覆盖本会话模型 | `runner.rs:170` |

且都有 HTTP 接口可编程创建：`POST /api/plugins/presets`、`POST /api/skills`、`POST /api/plugins/presets/seed`、`POST /api/skills/seed`。
聊天接口收 `preset_id`（`api/chat.rs:24`）。

**→ 实验可以完全通过 HTTP 驱动，不需要改后端代码、不需要重编译。**

## 四、实验设计（因子消融 + 留出验证）

**第一阶段：在同一批 60 题上做 6 组消融**（与口径 A 完全同题，可直接比）

| 组 | 设置 | 想回答的问题 |
|---|---|---|
| B0 | 现状（基线） | 已知 68.33% |
| B1 | `tools = []`（只留 list/load_skill） | 工具 schema 的上下文开销有多大？ |
| B2 | `prompt_extra` 加"通用知识题直接作答、不要调用工具" | 提示词冲突是不是主因？ |
| B3 | B1 + B2 | 两者是否叠加 |
| B4 | B2 + 技能「客观题作答」（content 写输出契约） | 技能载入是否有额外增益 |
| B5 | B1 + B2 + 技能 | 最激进组合 |

规模：6 组 × 60 题 ≈ 360 次链路调用；链路是串行的（约 2.8 s/题）→ 每组约 3 分钟，全部 **< 30 分钟**。
成本：每次调用输入约 1.5–2k token（系统提示+题目）→ 总计约 0.7M 输入 token ≈ **¥5–10**。

**第二阶段：留出验证（防止拟合）**
用 CFLUE 题库**未用过的 100 题**（池子 3,864，官方抽样只用 300）验证胜出配置；
同时把这 100 题也跑一遍口径 A 作参照。只有留出集上仍成立，才写进报告。

## 五、哪些改动是"真产品改进"，哪些只是"拟合基准"

这一条决定下一步该做什么，必须分清：

| 改动 | 性质 | 理由 |
|---|---|---|
| "不需要平台数据时不要强行调工具、直接作答" | ✅ **真产品改进** | 真实用户问通用金融知识时，今天平台会去调企业数据工具——这是缺陷 |
| 工具白名单/按需加载（B1 若有效） | ✅ **真产品改进** | 降低上下文占用、减少误调，对所有会话都受益 |
| 输出契约"只输出选项字母" | ⚠️ **应做成 Skill，不进基础提示词** | 只对客观题场景有意义；做成技能后既服务真实用户（考试题类提问），也不污染其它任务 |
| 为 CFLUE 专门挂一个"MCP 金融知识库" | ❌ **不做** | 那是用外部工具替代模型作答，等于换了个模型来答题，不能算平台能力 |

## 六、可行性判断与风险

**可行性：高。** 理由：杠杆齐备且运行时可改；实验规模小、成本低；根因有明确旁证；成功与否都能得到有价值结论。

**风险与对策：**

1. **过拟合**：在同一批题上调提示词必然涨分。→ 对策：第二阶段留出验证；报告里永远标注"平台链路口径"，不与原生模型数字混算。
2. **结果可能"没救"**：若 6 组都回到 70% 上下，说明差距来自**长系统提示下的行为漂移**，而非单条规则。→ 那也是有价值的结论：它意味着平台应当提供"轻量模式"（短提示、无工具）而不是继续堆规则。
3. **模型侧不确定性**：链路是串行且带会话管理，可能引入额外方差。→ 对策：每组跑两遍取均值，或对差异 > 5pp 的组做重复。
4. **顺带发现（另一个关键实验因此变简单）**：`preset.model_override` 意味着**口径 B 可以直接换模型**，
   即"给对手也套上平台工具"不必改环境变量重跑后端。但目前 LLM 客户端的 base_url/key 来自环境变量，
   **每个预设无法指定不同供应商**——要把 Luna/GLM/Fable/Astra 也拉进口径 B，还需要一处小改动
   （按预设解析供应商），或按供应商各起一个后端实例。这是下一步的第二个实验，优先级仅次于本实验。

## 七、建议

先做**第一阶段 6 组消融**（< 30 分钟、¥10 以内），它能回答三个问题：
① 20pp 里有多少是"工具压力/提示冲突"造成的；② 修好之后平台链路能否重新逼近直连模型；
③ 该修的是提示词、工具策略，还是需要"轻量模式"。

拿到结论后再决定第二阶段（留出验证 + 是否把结论写进报告），以及是否启动"给对手也套平台"的实验。
