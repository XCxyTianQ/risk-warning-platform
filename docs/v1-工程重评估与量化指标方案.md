# v1 工程重评估与量化指标方案

> 撰写日期：2026-09-13　｜　评估对象：当前 main（`19ecd40`，最新发布 v0.7.1）
> 触发背景：有质疑认为"这个项目太大了，做不了"。本文不辩解，先把**家底数字化**，再给出
> **v1 的量化验收标准**与**benchmark 方案**，最后落到里程碑与取舍。

---

## 一、结论摘要（先看这一段）

1. **"做不了"这个质疑，在"能不能跑通"这一层已经被证伪**：5 天、71 次提交、10 个版本，
   Windows/macOS 三平台 CI 全绿，桌面端装得上、跑得起来、功能闭环（数据 → 分析 → 预警 → 报告）。
2. **但质疑有合理内核**：我们目前所有证据都是**自证型**（自己写的探针、自己的冒烟），
   **没有一个外部可比、可复现的量化指标**。这就是"能用"与"生态"之间真正的差距。
3. 因此 v1 的定义不是"再加功能"，而是：**把已有能力用数字说清楚**——
   自建 `FinRisk-Bench`（专属）+ 抽样对接外部公开基准（可比）+ 一条命令产出可归档的评测报告。
4. 最大的硬缺口是**数据规模**：现在整个库只有 **127 行**（5 家企业），
   而"风险预警"这件事的可信度完全建立在样本量上。这是 v1 必须补的第一块。
5. 工作量可控：评测 harness **不需要新平台**，直接复用现有 12 个探针 + 9 个 Electron 冒烟的写法，
   1 人 1 周可以让"指标看板"先跑起来。

## 四、Benchmark 方案

### 4.1 外部基准（解决"可比性"）

原则：**不全量跑**（成本与时间不可控），统一按"固定种子抽样 + 版本锁定 + 记录 harness 版本"的方式跑，
报告里给出样本量与 95% 置信区间。以下基准的具体切分与题量，动手前逐个到官方仓库核对。

| 组别 | 基准 | 用来回答什么问题 | 我们的指标 |
|---|---|---|---|
| 中文金融知识与推理 | CFLUE（ACL 2024 Findings，[论文](https://aclanthology.org/2024.findings-acl.337/)、[仓库](https://github.com/aliyun/cflue)）、FinEval（[论文](https://aclanthology.org/2025.naacl-long.318.pdf)）、CFBenchmark（[数据集](https://huggingface.co/datasets/TongjiFinLab/CFBenchmark)） | 模型在中文金融语境下的基础理解是否够用 | 抽样 500 题的准确率、按任务分组的准确率、与公开榜单分位对比 |
| 金融文档问答（RAG） | FinanceBench 风格的"财报问答"（[数据/评测仓库](https://github.com/patronus-ai/financebench)） | 文档检索 + 证据引用 + 数值作答是否可靠 | 答案准确率、**引用可核验率**、检索命中率（Recall@k）、拒答正确率 |
| 表格结构理解 | FinTabNet / PubTabNet / TableBench 类表格结构任务 | 复杂表格（多级表头、合并单元格）解析能力 | TEDS / S-TEDS、单元格级 F1 |
| 多模态文档解析 | OmniDocBench（[仓库](https://github.com/opendatalab/OmniDocBench)）、CC-OCR | 中文财报 PDF/截图读取质量 | 文本编辑距离、公式 CDM、表格 TEDS、阅读顺序编辑距离 |
| Agent 工具调用 | BFCL v3、τ²-bench、MCP-Universe（可经 [mcp-adapted-bench](https://github.com/Raibows/mcp-adapted-bench) 适配 MCP） | 25 个工具 + MCP 接入的调用是否正确 | 工具选择正确率、参数 exact-match、任务完成率、平均步数、无效/越权调用率 |
| 多语言多模态金融 | MultiFinBen（[论文](https://www.semanticscholar.org/paper/MultiFinBen%3A-Benchmarking-Large-Language-Models-for-Peng-Qian/708d820657bcbbe8cec5118d967791f282e26340)） | 作为加分项，检验泛化 | 分任务准确率 |

### 4.2 自建专属基准：FinRisk-Bench（解决"专属生态"）

这是 v1 最该产出的资产：**别人没有的、贴合"企业经营风险预警"的评测集**。

**数据来源**

1. 上市公司公开年报（巨潮/交易所）：三表 + 附注 + PDF/截图 → T1–T4
2. 风险事件样本：ST/\*ST、退市、监管处罚、债务违约企业（事后事件即天然标签）→ T5
3. 扰动注入（合成）：单位错位（元/万元/亿元）、千分位、括号负数、勾稽破坏、跨期错配、
   低质图片（模糊/倾斜/遮挡/水印/压缩）→ T2/T3 的负例与鲁棒性
4. Agent 意图集：由 25 个工具反推 120+ 条"问题 → 期望工具与参数"，
   含三类负例（该拒答、该走审批、该追问澄清）

**任务分层与指标**

| 层 | 任务 | 样本量（v1 目标） | 指标 |
|---|---|---:|---|
| T1 | 三表科目结构化抽取 | ≥ 300 科目行 | 字段级 P/R/F1、数值 MAPE、单元格定位准确率 |
| T2 | 图片/扫描财报读取 | ≥ 150 张 | 字段准确率、置信度校准（ECE）、**该拒识的拒识率** |
| T3 | 勾稽与一致性校验 | ≥ 200 注入样本（每类 ≥ 25） | 检出率（Recall）、误报率（FPR）、定位准确率 |
| T4 | 指标测算（KPI/杜邦/Z·F·M） | ≥ 200 企业·期 | 与参考实现逐点比对：一致率、相对误差分布 |
| T5 | 风险评级与预警 | ≥ 120 家（风险/对照各半） | ROC-AUC、PR-AUC、KS、Top-K 命中率、**提前预警期中位数** |
| T6 | Agent 工具链 | ≥ 120 条 | 工具选择正确率、参数 exact-match、完成率、平均步数、越权拦截率 |
| T7 | 报告生成质量 | ≥ 60 份 | 数字可核验率、无来源数字比例（幻觉率）、双人评分 + Cohen's κ |
| T8 | 运行指标 | 全链路 | p50/p95 时延、单次 token 成本、缓存命中率、错误率 |

**打分与报告**

- 一条命令产出：`bench-report.json` + `bench-report.md`（含 commit、模型、harness 版本、随机种子、样本 hash）
- 确定性优先：能自动判定的（T1/T3/T4/T6/T8）一律自动；主观项（T7）双人标注 + κ ≥ 0.7 才采信
- 防作弊：测试集 hash 冻结；工具层禁止读取 `bench/` 目录；prompt 里不得出现测试样本原文
- 可对比：报告支持多模型/多版本横向表格（DeepSeek 与其他模型）

### 4.3 与质疑的对齐（答辩三句话）

1. **"我们不是做了很多功能"** → 25 个工具在 BFCL/τ²/MCP 抽样上工具选择正确率 X%、越权调用 0 次
2. **"我们能证明效果"** → 自建 FinRisk-Bench：T1 字段 F1 = X、T3 检出率 X% / 误报 X%、T5 PR-AUC = X、提前预警中位数 X 天
3. **"我们算得清成本"** → 单企业全链路 ¥X、p95 X 秒、缓存命中 X%

## 七、风险与取舍（诚实清单）

1. **外部基准的许可与体量**：部分数据需申请或体积很大 → 只做抽样，记录版本与样本 hash，不宣称"跑过全量"。
2. **T5 的因果性弱**：ST/处罚是"事后标签"，不等于平台预警能力 → 用提前预警期 + PR-AUC 表述，明确不做因果结论。
3. **单模型风险**：所有指标绑定一个 LLM 供应商 → 至少两个模型对照，报告中写明模型与版本。
4. **人力约束**：只有 1 人能写代码 → harness 不做平台化，直接复刻探针模式；标注工作必须由另外 4 人承担。
5. **指标被"调"出来**：先冻结测试集（hash + 版本），再优化；禁止针对测试集改 prompt，改动须记录在报告里。
6. **数据合规**：只用公开数据；报告与产品均保留"不构成投资建议"声明。

### 9.8 升级兼容 P0：旧数据目录上的写路径曾经是坏的（2026-09-13 发现并修复）

**怎么发现的**：接入真实模型后，我拿用户的真实数据目录做一次端到端对话，接口直接返回
`NOT NULL constraint failed: chat_session.summary` —— 也就是说**升级到 Rust 版本后，新建会话一直是失败的**
（该库里 `chat_session`/`chat_message` 都是 0 行，与"从未成功建过会话"一致）。
根因：旧库（Python/SQLAlchemy 建的表）里大量列是 `NOT NULL` **却没有 DEFAULT**，而 Rust 侧的
INSERT 只写自己关心的列、其余依赖默认值补齐（`chat_session` 只插 4 列）。
所有用全新临时目录的测试都发现不了——**这正是"评测框架必须覆盖真实升级路径"的价值**。

**影响面（脚本扫描全部 INSERT × 旧 schema 得出）**：

| 表 | 旧库缺失且 NOT NULL 无默认值的列 | 后果 |
|---|---|---|
| `chat_session` | summary / compacted_until / compact_count / pinned / share_token / 4 个用量列 / est_cost | 新建对话失败（500） |
| `enterprise` | unified_code / legal_rep / reg_capital_wan / reg_date / address | 新增企业失败 |
| `alert` | handler / notes_json | 生成预警失败 |

**修复**：`db::migrate()` 新增通用的"旧表重建"——解析 `schema.rs` 里的建表语句，
凡"旧列 NOT NULL 无默认值、而新 schema 给了默认值"的表，就
`RENAME → 按新 schema 建表 → 拷贝列交集 → DROP 旧表`（一个事务内完成）。
两个必须踩过的坑：① `PRAGMA legacy_alter_table=ON`，否则 SQLite 会把**别的表**里
`REFERENCES 本表(id)` 一起改写成临时表名，删表后那些表永久引用不存在的表
（表现为之后 `POST /api/tables` 报 `no such table: enterprise__legacy_backup`）；
② 重建会丢掉索引，所以在 `Db::open` 里再跑一遍 SCHEMA（全部 `IF NOT EXISTS`）补回来。

**验证（三层）**：

1. 新增 `legacy-db-compat` 套件 + 随仓库提交的旧库夹具
   `backend/tests/fixtures/legacy-python-schema.sql`（由 Python 参考实现首次启动自动建表导出，
   只含表结构与两条演示企业），跑通会话/表格/企业建档/读路径 13 项断言；
2. 先在修复前的 0.7.1 二进制上跑 → **红**（复现 `chat_session.summary` 500）；
   修复后 → **绿**；
3. **拿用户真实库的副本做迁移预演**：13 张表重建、`enterprise 5 / finance 8 / news 58 / legal 21 /
   skill 5 / agent_preset 4 / app_setting 13` 全部零丢失，新建会话与新建表格均 200，日志无错误。

> 结论：这不是"改完就跑"的补丁，而是**先有夹具、先复现、再修、再证明零数据丢失**的闭环。

产出 `label-validation.json`（覆盖/一致性/召回缺口/样例）与 `review-queue.jsonl`
（411 条待人工复核，带 `reason` 与置信度分级 A/B/C）。

**验证抓到的两个真问题**（比数字更重要）：

1. **关键词检索有系统性漏检**——"可能被终止上市的风险提示""股票交易被叠加实施其他风险警示"
   这类标题靠词表检索抓不全；两条独立路径（全量扫描 / 交易所官方）能补上；
2. **词表有噪音**——`资金占用` 命中 6.8 万条，大多是例行披露的
   "非经营性资金占用及其他关联资金往来（汇总）表/专项审计报告"，不是风险事件；已收紧排除词。
   同时把债券违约/兑付违约/实质违约/展期纳入词表（B6 的上市公司口径部分）。

**拿不到的数据（实测被挡，附证据）**：

| 想要的数据 | 尝试 | 结果 |
|---|---|---|
| 东财违规/处罚/债券违约/失信库 | 11 个 `reportName` | 全部 `报表配置不存在 (9501)` |
| 失信被执行人 / 被执行 | 执行信息公开网 `zxgk.court.gov.cn` | `404 / 412`（反爬 + 验证码） |
| 非上市企业工商信息 | 国家企业信用信息公示系统 `gsxt.gov.cn` | `521` + JS cookie 挑战 |
| 上交所公告/纪律处分 | `query.sse.com.cn` | `SOA service missing parameter [siteId]`（参数未公开） |

**结论**：B6 的"债券违约"只能覆盖**上市公司披露口径**；"失信/被执行企业"与 B7 的"非上市企业"
**目前没有可用公开接口**，需要付费数据源或人工抽样——不假装能做。
若要继续，需要决策：是否采购企业征信 API（预算），否则这三块保持"已识别、未覆盖"状态。
