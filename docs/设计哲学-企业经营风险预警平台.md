## 一、问题形式化

### 1.1 传统范式的隐含假设

传统企业风险评估建立在四条隐含假设之上：

- **A1（结构化）**：风险信号主要存在于低频、定周期的结构化数据（季报、年报、评分卡字段）中；
- **A2（可穷尽）**：投入足够人力即可完成信息采集，不存在"采集不到"的状态；
- **A3（分数即结论）**：一个 0～100 分与一个 AAA～C 评级足以表达风险全貌，推理过程无需外化；
- **A4（事后确认）**：风险在公开暴露后才进入评估视野。

A2 与 A3 共同导致一个工程后果：系统对"数据缺失"缺乏表达能力，只能以默认值填充——而这恰恰是风险判断中最危险的一类静默错误。

### 1.2 新约束条件

多模态大模型与公开数据生态的成熟，引入了六条新的硬约束：

| 编号 | 约束 | 工程含义 |
|---|---|---|
| C1 | 非结构化信息可读但昂贵 | 文本/图像/表格可被模型理解，但每次理解都消耗 token |
| C2 | 数据源不稳定且不可穷尽 | 免费接口存在失败与限流，必须显式建模"无数据" |
| C3 | 模型输出不可完全信任 | 存在幻觉，需以规则、证据与置信度约束 |
| C4 | 结论必须可追溯 | 金融场景要求证据来源、时间与引用可核验 |
| C5 | 成本与延迟有上限 | 长上下文、多轮工具调用会显著放大费用 |
| C6 | 交付环境不可假设 | 需在普通 Windows 单机上独立运行，无云端运维 |

### 1.3 设计目标

在上述约束下，系统必须同时满足四个目标：

- **O1 正确性优先于覆盖率**：宁可输出"数据不足"，不输出伪确定结论；
- **O2 可追溯性**：任一结论都能定位到证据及其来源与时间；
- **O3 成本可预测**：单位对话成本有界且可观测，不随会话长度线性爆炸；
- **O4 可独立交付**：单机可运行、双击即用、无外部依赖。

### 1.4 核心命题

> 在 C1–C6 约束下，构建一个满足 O1–O4 的风险预警系统，其关键在于：**把"缺失"建模为一等状态、把"证据"作为结论的强制前置、把"前缀"视为可缓存的稀缺资源。**

## 二、设计哲学

### 2.1 Agent 为体，工具为用

**形式化定义**：设模型输出空间为 M，数据空间为 D，动作空间为 A。模型不持有对 D 与 A 的直接引用；一切访问经由工具集合 T = {t₁, …, tₙ}，其中 tᵢ = (schemaᵢ, handlerᵢ, read_onlyᵢ)。模型仅能通过生成符合 schemaᵢ 的 JSON 参数来调用 tᵢ。

**机制**：`ToolRegistry` 是唯一注册表。循环内工具调用统一经 `registry.call(name, args, db)` 分发；异常被捕获并转为文本 `"ERROR: {message}"` 回注给模型，而非抛出中断循环——这保证了模型有机会自行调整策略。

```python
# 伪代码：工具分发
def call(name, args, db):
    tool = self._tools.get(name)
    if tool is None: return {"error": f"unknown tool: {name}"}
    try:
        return tool.handler(db, **args)
    except TypeError as e:      # 参数不符合 schema
        return {"error": f"参数错误: {e}"}
    except Exception as e:      # 业务异常
        return {"error": f"{type(e).__name__}: {e}"}
```

**数据结构**：

| 字段 | 类型 | 语义 |
|---|---|---|
| `name` | str | 工具名（OpenAI function 命名约束：`^[A-Za-z0-9_-]{1,64}$`） |
| `description` | str | 供模型判断调用时机的自然语言说明 |
| `parameters` | dict | JSON Schema |
| `handler` | Callable | 签名 `(db, **kwargs) -> dict` |
| `read_only` | bool | `False` 时触发 Approval 流程 |

**量化**：内置工具 14 个；外部 MCP 工具按服务动态注册（命名 `mcp_{server_id}_{tool_name}`，截断至 64 字符）；用户插件命名 `custom_{name}`，同样截断至 64 字符。

**取舍**：工具化引入一次额外的"意图表达—参数解析"开销（模型需以 JSON 描述调用），相比直接函数调用延迟更高。接受该开销，换取可审计（每次调用留痕）、可授权（写操作可拦截）、可扩展（新增能力无需修改循环）。

### 2.2 没有数据 ≠ 没有风险

**形式化定义**：对维度 d，定义数据状态 σ(d) ∈ {ok, empty, never, error}，评分函数 s(d) 的取值规则如下：

| 数据状态 σ(d) | 评分 s(d) | 语义 |
|---|---|---|
| ok | score_d(indicators) | 采集成功且有记录，按该维度公式计算 |
| empty | 100 | 采集成功但无记录，视为无负面信号 |
| never | ⊥（未定义） | 从未采集，不参与评分 |
| error | ⊥（未定义） | 采集失败，不参与评分 |

综合评分仅在存在已定义维度时计算：

```
S = (Σ s(d)) / n        n = 已定义维度个数（s(d) ≠ ⊥）
S = ⊥  ⟺  所有维度的 s(d) 均为 ⊥
```

**起源（真实缺陷）**：系统早期版本对不存在的企业（如"中色集团"）执行评分时，三个数据源均无记录，而评分逻辑将"无涉诉记录""无负面舆情"解释为"零风险"，输出 **100 分 / AAA**。缺陷根因是 A2 假设的残留——把"信息缺失"等同于"风险缺失"。

**机制**：`Enterprise.data_status_json` 持久化每维状态；`refresh_enterprise()` 依据采集结果写入状态；`rules.dim_score()` 在状态为 `never`/`error` 时返回 `(None, note)`。所有维度均无定义时，`rules_verdict()` 返回 `score=None, grade="—", level="gray"`，前端展示"无数据，无法评估"。

**状态转移**：

```
never ──采集成功且有记录──▶ ok
never ──采集成功但无记录──▶ empty
never ──采集失败──────────▶ error
ok/empty ──再次采集成功──▶ ok 或 empty（按本次结果）
error ──重试成功──────────▶ ok 或 empty
```

**配套防线**：添加企业时若名称无法严格解析为证券代码，或三源均无记录，系统撤销建档并返回错误，避免产生"空壳企业"。

**量化**：该修复后，虚假企业查询返回 `score=None / grade=— / level=gray`；真实非上市企业（深度求索）财务维度为 `never`（灰显），其余五维正常参与评分（90.0 分 / AAA）。

### 2.3 证据先于结论

**形式化定义**：风险事实集 F = {f₁, …, f_k}，每条事实 fᵢ = (text, dimension, source, date, confidence, raw_ref)。模型输出的结论必须满足：结论中的每一项判断都能映射到 F 的子集；无对应事实的判断被要求标注为"推断"。

**机制**：提示词强制要求"证据必须逐条来自工具返回的数据，不得编造"；工具返回的事实携带来源与时间；预警工单的 `evidence_json` 直接由事实构成；导出的 Markdown 报告逐条列出证据及来源。

**数据结构（`risk_fact`）**：

| 字段 | 类型 | 语义 |
|---|---|---|
| `enterprise_id` | int | 关联企业 |
| `dimension` | str | 六维之一 |
| `text` | text | 事实描述 |
| `evidence_json` | text | `{"source": ..., "date": ...}` |
| `confidence` | float | 置信度（当前默认 0.8） |
| `ts` | datetime | 生成时间 |

**取舍**：强制引用会限制模型自由度并增加输出长度（token 成本）。在风险场景中，"可核验但冗长"优于"简洁但无从查证"。

### 2.4 稳定前缀，善用缓存

**缓存模型**：设请求的 token 序列为前缀 P 与可变部分 V 的拼接（记作 P + V）。提供方缓存 P 的 KV 表示；当两次请求的 P 完全一致时命中，命中部分按缓存价计费。因此单次请求成本近似为：

```
Cost ≈ (|P_hit| / 10^6) · p_hit
     + ((|P_miss| + |V|) / 10^6) · p_miss
     + (|O| / 10^6) · p_out

|P_hit| 命中缓存的输入 token 数    |P_miss| 未命中的输入 token 数
|V|     新增可变内容 token 数        |O|     输出 token 数
p_hit / p_miss / p_out 分别为命中、未命中与输出的单价（元/百万 token）
```

**三条硬约束**（由缓存模型直接导出）：

| 约束 | 违反后果 | 实现 |
|---|---|---|
| 系统提示词静态 | 前缀首 token 变化 → 全量缓存失效 | `agent/prompt.py` 不含时间戳/企业名等易变内容 |
| 工具 schema 稳定 | token 序列缩短 → 后续 token 失配 | 注册表启动时构建，顺序固定 |
| 历史追加式 | 改写历史 → 前缀漂移 | 消息仅 append；压缩锚定在头部 |

**压缩调用的前缀复用**：DeepSeek Harness 的 `2026-07-21-compaction-summary-prefix-cache-reuse` 记录了一个反例——若摘要调用另起一个"摘要器 system 提示词"，则第一个 token 即不同，整个已缓存前缀失效，恰好在上下文最长时为全量历史付出两次全价。本系统的做法是**逐字复现已路由请求的前缀，在末尾追加压缩指令**，并保留 `tools` 以维持序列对齐：

```python
messages = [*base_messages, {"role": "user", "content": COMPACTION_INSTRUCTION}]
client.chat(messages, tools=tools, max_tokens=settings.compaction_summary_max_tokens)
```

**预热协议**：以与真实请求完全相同的 system 与 tools 发送一个 `max_tokens=1` 的最小请求，把静态前缀提前写入缓存。触发时机：服务启动、新会话首个请求、压缩完成后（前缀已变化）、设置中切换模型/端点后。

**量化**（真实 API，连续四轮追问）：

| 轮次 | 输入 token | 缓存命中 | 命中率 |
|---|---|---|---|
| 1 | 7,012 | 6,400 | 91.3% |
| 2 | 13,423 | 12,544 | 93.5% |
| 3 | 16,972 | 16,000 | 94.3% |
| 4 | 20,518 | 18,048 | 88.0% |

会话整体命中率 87.96%；预热后新会话首个请求命中 2,048 / 2,063 token（**99.3%**）。

### 2.5 上下文是稀缺资源

**形式化定义**：设模型窗口为 W，上下文构造函数为 g(·)，则对任意会话长度恒有：

```
|g(session)| ≤ α·W + β
```

即上下文体积与会话长度无关：α 为保留比例（可变部分上界），β 为摘要与系统提示的固定开销。

**机制一：压缩**。当估算用量达到 W × 0.8 时触发，折叠至保留预算 W × 0.16，摘要作为 system 消息置于压缩点之后的历史之前。折叠时保持工具调用配对完整（禁止在 `assistant(tool_calls)` 与 `tool` 之间切断）。

**机制二：渐进式披露**。技能不全文注入提示词：`list_skills` 仅返回名称与描述，模型判断相关后再 `load_skill(name)` 载入完整指令。MCP 工具与自定义插件同理按需注册。

**取舍**：压缩会丢失细节（以摘要替代原文），渐进披露增加一次工具往返。二者都以"上下文体积有界"为最高优先级。

### 2.6 写操作必须授权

**形式化定义**：工具集合按 `read_only` 划分为只读集合 T_ro 与动作集合 T_rw。对任意 t ∈ T_rw，其执行前置条件为存在用户授权决策 δ ∈ {approved, rejected, timeout} 且 δ = approved。

**机制（挂起而非阻塞轮询）**：

```python
# 动作工具执行路径
pa = approvals.create(session.id, tool_call_id, name, args, description)
yield AgentEvent("approval", {...})            # 推送授权请求
decided = pa.event.wait(timeout=settings.agent_approval_timeout)   # 挂起等待
approved = bool(decided and pa.approved)
if not approved:
    # 超时或拒绝：以工具结果形式回注，使对话自然继续
    result = {"error": "用户拒绝执行该操作" if decided else "等待授权超时（300s）"}
```

**事件与接口**：`approval` 事件携带 `approval_id / name / args / description / timeout`；前端通过 `POST /api/chat/approve {approval_id, approved}` 恢复。授权决定与审批记录不进入模型上下文之外的持久化路径，避免污染历史。

**取舍**：审批增加交互步骤。风险系统中"误操作成本"高于"多点一次的成本"。

### 2.7 组合优于继承

**形式化定义**：Agent 行为由四元组配置 (prompt_extra, T_allow, S_allow, m_override) 决定，而非通过类型派生。当白名单为空时视为全集。

**机制**：`build_registry(preset)` 在构建注册表时按白名单裁剪；`list_skills` / `load_skill` 按技能白名单过滤（二者始终保留，以支持技能发现）。模型覆盖仅影响本次运行的 `LlmConfig`，不修改全局设置。

**可移植性**：预设、技能与插件可打包为 JSON 分享包（`kind: risk-warning-agent-bundle`），导入时对**内容一致**的技能与同名且 URL+方法一致的插件自动复用，避免重复副本；`version` 高于平台支持时拒绝导入。

**取舍**：组合带来配置空间膨胀的风险（预设数量 × 白名单组合）。以三个内置预设收敛常见场景，并提供"导出/导入"以便团队共享经过验证的组合。

### 2.8 单机可交付

**形式化定义**：系统在无外部服务依赖（除模型 API 与公开数据源）的条件下，可在单台 Windows 主机上完成安装、运行与数据持久化。

**机制**：SQLite 存储；Electron 主进程探测空闲端口并拉起内嵌后端（开发态为 venv Python，发布态为 PyInstaller onedir 产物）；数据与日志落于 `%APPDATA%\RiskWarningPlatform\`；首次运行自动灌入样例企业数据。

**进程模型**：

```
Electron 主进程
  ├─ 单实例锁（requestSingleInstanceLock）
  ├─ 端口探测（net.createServer listen(0)）
  ├─ spawn 后端 → 轮询 GET /api/health（超时 90s）
  ├─ BrowserWindow 加载 http://127.0.0.1:<port>
  └─ before-quit → taskkill /PID <pid> /T /F（清理进程树）
```

**量化**：安装包 139.2 MB / 便携版 139 MB / 免安装目录 429 MB；后端目录 110.6 MB（主程序 26.3 MB）；前端产物 1.31 MB。

## 三、灵感来源与工程借鉴

本平台的每一条机制都能追溯到具体的工程来源。区分"借鉴"与"照搬"很重要：借鉴的是**约束条件下的解法**，照搬则往往把不属于本场景的复杂度一并带入。以下按来源逐项说明。

### 3.1 DeepSeek Harness：Agent 运行时与上下文工程

DeepSeek Harness（DSH）是一个可组合的 Agent 运行时，对本平台影响最直接：

| 借鉴机制 | 来源要点 | 本平台适配 |
|---|---|---|
| Agent 循环 | 模型与工具交替，工具结果以文本回注 | 保留；`MAX_STEPS=5` 限制单轮成本 |
| 事件流协议 | 会话/文本/工具/用量/压缩/审批/结束分事件推送 | 保留；事件名与载荷字段对齐 |
| 写操作审批 | 动作执行前挂起，等待用户决策 | 保留；由工具 `read_only` 标记驱动 |
| 技能渐进披露 | 先列出技能名与描述，再按需载入全文 | 保留；技能不进入静态前缀 |
| 压缩参数 | `thresholdRatio=0.8`、`retainRatio=0.16` | 保留默认值，改为可配置 |
| 压缩的前缀复用 | 摘要调用必须复用已路由前缀，否则整段缓存失效 | 保留，并成为缓存策略的核心约束 |
| 预设即组合 | 预设是能力行的组合，而非继承体系 | 简化为四元组配置（见 2.7） |

**关键工程笔记**：DSH 的 `2026-07-21-compaction-summary-prefix-cache-reuse` 记录了一次真实故障——摘要器另起 system 提示词导致首个 token 失配，恰在上下文最长时全量重算。本平台把该结论固化为 `compact()` 的实现约束（见 2.4）。

**未照搬的部分**：DSH 的预设是完整的 Cordis 插件组合（含依赖解析与服务隔离），面向多会话宿主；本平台是单机单用户工具，四元组配置已足够表达全部场景，引入插件依赖解析会带来不成比例的复杂度。

### 3.2 OpenAI function calling：工具契约与用量回传

- **工具契约**：采用 OpenAI 兼容的 `tools` / `tool_calls` 协议，参数以 JSON Schema 描述。选择它的原因是生态兼容性——模型提供方、MCP 与第三方插件共用同一契约，无需为每种能力另写适配。
- **流式用量**：`stream_options={"include_usage": True}` 在流末尾返回 `usage`，本平台据此实现逐次调用的缓存命中统计（见 2.4）。
- **多模态输入**：`content` 支持 `[{type:"text"}, {type:"image_url"}]` 结构，为财报截图与公告图片的解析预留通道。

**未照搬的部分**：未采用 Assistants API 的服务端状态管理，会话状态由本平台自持（SQLite），以保证离线可用与数据主权。

### 3.3 Anthropic prompt caching：前缀稳定的三条约束

Anthropic 的缓存文档把"前缀稳定"提升为一等约束（以 `cache_creation_input_tokens` / `cache_read_input_tokens` 显式区分读写）。本平台把该语义映射为提供方的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，并据此推出三条实现约束（见 2.4）。

**差异**：Anthropic 需显式标注缓存断点，本平台面向自动前缀缓存的提供方，因此以"绝不扰动前缀"替代"标注断点"。

### 3.4 ReAct 范式：推理与行动交替

ReAct 提出推理（Reasoning）与行动（Acting）交替的循环，使模型能在信息不足时主动获取信息。本平台的差异在于**收敛性约束**：工具调用上限 5 轮、单条工具结果截断 6000 字符。ReAct 关注能力上限，本平台同时关注成本上限。

### 3.5 信用评分卡：六维扣分制与评级映射

六维结构与 AAA~C 评级借鉴自企业信用评级与商业银行内部评分卡实践：分维度独立计分、扣分制、分级映射、上限封顶。

**关键改造**：评分卡传统上要求字段完整，缺失时以均值或行业基准填充；本平台改为**缺失即不参与评分**（见 2.2）。理由是风险场景中"编造一个中性值"比"承认无数据"危险得多——前者会产生可执行的错误结论。

### 3.6 AkShare 与公开数据生态

数据源选择遵循"公开、可追溯、可替换"三原则：财务取东财摘要接口（失败时回退新浪），舆情合并东财新闻与公告，法律取巨潮诉讼统计。适配层协议（见 4.6）使数据源可插拔——新增来源只需实现 `fetch()` 并注册优先级，不改动评分与预警逻辑。

**合规边界**：仅使用公开或授权数据，不绕过验证码与访问控制，保留来源与采集时间，不转售数据。

### 3.7 单机交付：SQLite + PyInstaller + Electron

交付方案来自对"评审现场"这一真实场景的观察：评审不会为观看演示而安装 Docker 与数据库。因此选择 SQLite（零运维）、PyInstaller（免 Python 环境）、Electron（原生窗口、托盘与单实例）。代价是安装包体积（139 MB），收益是"双击即用"。

### 4.2 Agent 循环

**状态机**：

```
IDLE ──user message──▶ CONTEXT_ASSEMBLY
CONTEXT_ASSEMBLY ──压力检查──▶ COMPACTION（可选）──▶ LLM_CALL
LLM_CALL ──tool_calls──▶ TOOL_EXECUTION ──回注──▶ LLM_CALL（≤5 轮）
LLM_CALL ──纯文本──▶ PERSIST ──▶ IDLE
LLM_CALL ──异常且为溢出──▶ 强制压缩 ──▶ LLM_CALL（一次）
```

**伪代码**：

```python
def run_agent(db, session, user_text, preset_id=None):
    store.append(db, session, {"role": "user", "content": user_text})
    reg = _registry_for(db, preset)          # 内置（按预设裁剪）+ 插件 + MCP
    messages = _build_messages(session, system_prompt)
    yield from _maybe_compact(db, session, client, reg, messages)   # 主动压力检查
    for step in range(MAX_STEPS):            # MAX_STEPS = 5
        messages = _build_messages(session, system_prompt)
        text, tool_calls = stream_call(client, messages, reg.definitions())
        yield usage_event(client.last_usage) # 缓存命中/未命中 token
        if tool_calls:
            for tc in tool_calls:
                if not tool.read_only and require_approval:
                    yield approval_event(...); wait_for_decision(...)
                result = reg.call(name, args, db)
                store.append(db, session, tool_message(result))
                yield tool_result_event(summarize(result))
            continue
        store.append(db, session, {"role": "assistant", "content": text})
        yield done_event(usage_stats(session)); return
```

**事件协议**：

| 事件 | 载荷 | 前端行为 |
|---|---|---|
| `session` | `session_id, title` | 记录会话、写入 localStorage |
| `token` | `text` | 追加流式文本 |
| `tool` | `id, name, args, read_only` | 渲染工具卡片（运行中） |
| `tool_result` | `id, name, result(摘要)` | 更新卡片；按结果类型自动开窗 |

| `error` | `message` | 展示错误 |

### 4.3 上下文压缩算法

```python
def estimate_tokens(messages, tools=None):
    # 中文约 1 字≈0.7 token，英文约 4 字符≈1 token；保守取字符数/1.6
    total = 0
    for m in messages:
        content = m.get("content") or ""
        if isinstance(content, (list, dict)):
            content = json.dumps(content, ensure_ascii=False)
        total += int(len(str(content)) / 1.6) + 6          # 每条消息固定开销
        for tc in m.get("tool_calls") or []:
            total += int(len(json.dumps(tc, ensure_ascii=False)) / 2.5) + 4
    for t in tools or []:                                  # 工具 schema 计入上下文
        total += int(len(json.dumps(t, ensure_ascii=False)) / 2.5) + 4
    return total

def should_compact(messages, tools):
    est = estimate_tokens(messages, tools)
    return est >= settings.llm_context_window * settings.compaction_threshold_ratio, est

def _split_for_compaction(session):
    active = [m for m in session.messages if m.id > session.compacted_until]
    retain_budget = settings.llm_context_window * settings.compaction_retain_ratio
    kept, used = [], 0
    for m in reversed(active):               # 自后向前累计至保留预算
        used += estimate_tokens([m])
        if used > retain_budget and kept: break
        kept.insert(0, m)
    fold = active[:len(active) - len(kept)]
    while fold and fold[-1].role == "assistant" and fold[-1].tool_calls:
        fold.pop()                            # 不变式：不切断 tool 配对
    return fold, fold[-1].id if fold else 0
```

**参数**：`llm_context_window=128000`、`compaction_threshold_ratio=0.8`、`compaction_retain_ratio=0.16`、`compaction_summary_max_tokens=1024`。

**不变式**：

- I1：压缩后 `store.context()` 返回 `[摘要 system 消息] + 压缩点之后的最近消息`；
- I2：`compacted_until` 单调不减；
- I3：任何时刻不得出现孤立的 `tool` 消息（其对应的 `assistant(tool_calls)` 已被折叠）。

### 4.5 六维评分公式

| 维度 | 基础分 | 扣分项（阈值与上限） | 门控条件 |
|---|---|---|---|
| 财务健康 | 100 | 资产负债率 ≥85% −45 / ≥70% −30 / ≥60% −15；净利润 <0 −25；连续两年亏损 −10 | `finance=ok` 且财报可用 |
| 法律合规 | 100 | 每条司法/行政记录 −6（上限 −50）；行政处罚 −10（上限 −25）；刑事 −20（上限 −20）；商标行政 −4（上限 −15）；涉案 ≥1 亿 −10 | `legal ∈ {ok, empty}` |
| 舆情声誉 | 100 | 负面占比 × 120（上限 −60）；近一年负面每条 −3（上限 −15） | `news ∈ {ok, empty}` |
| 经营能力 | 95（有年限）/ 90（无年限） | 成立 <2 年 −10 / <5 年 −5 / ≥10 年 +5；净利润率 <0 −30 / <5% −8 / >20% +3；营收增速 <0 −15 / >20% +3 | 有成立年限，或有财务派生的利润率/增速 |
| 信用状况 | 100 | 失信 −40/次（上限 −45）；被执行 −30/次（上限 −35）；行政处罚 −12/次（上限 −25） | `legal ∈ {ok, empty}` |
| 供应链稳定 | 100 | 合同类纠纷 −8/项（上限 −45）；供应链负面舆情 −8/条（上限 −25） | `legal` 或 `news` 至少一项已采集 |

**评分离散化**：所有维度得分经 `_clamp(v) = int(max(0, min(100, round(v))))` 处理，保证输出为 [0,100] 内的整数，避免浮点抖动导致评级跳变。

**评级映射**：AAA ≥90 · AA 80–89 · A 70–79 · BBB 60–69 · BB 50–59 · C <50。
**风险等级映射**：≥85 绿 · 70–84 黄 · 55–69 橙 · <55 红 · 无数据 灰。

**交叉校验**：规则引擎输出 `rules_level`，模型输出 `llm_level`；不一致时以规则为准并标记 `cross_check_ok=false`。实测样例（康美药业）：`llm_level=red`、`rules_level=red`、`cross_check_ok=true`、证据 21 条覆盖全部六维。

### 4.7 预警闭环

**状态机**：

```
(pending) ──start──▶ (handling) ──resolve──▶ (resolved)
    │                     │
    │                     └──ignore──▶ (ignored)
    └──ignore──▶ (ignored)         (resolved|ignored) ──reopen──▶ (pending)
```

**生成规则**：维度得分 <85 触发工单，等级按 <55 红 / 55–69 橙 / 70–84 黄；综合等级为红/橙时追加一条综合工单。**幂等键** `fingerprint = "{enterprise_id}:{dimension}:{level}"`，与未关闭工单（`pending`/`handling`）比对后跳过。

**审计记录**（`alert.notes_json`，追加式）：

```json
[{"ts": "...", "action": "resolve", "status": "resolved",
  "status_label": "已处置", "handler": "张三", "note": "已核实并联系企业"}]
```

**量化**：对 7 家企业批量生成 18 条工单（红 8 / 橙 3 / 黄 7）；同一批次重复生成时全部命中幂等键而跳过。

### 4.8 MCP / 技能 / 预设

**MCP 协议**：HTTP JSON-RPC 2.0（`POST <url>`，body 为 `{"jsonrpc":"2.0","id":n,"method":...,"params":{...}}`），实现 `initialize` / `ping` / `tools/list` / `tools/call` 四个方法；客户端工具以 `mcp_{server_id}_{tool_name}` 注册，服务级 `require_approval` 决定其工具是否为动作类。本平台同时实现服务端：`POST /api/mcp` 以同一协议对外暴露全部 14 个内置工具（未知方法返回 `-32601`，缺参返回 `-32602`）。

**技能渐进披露**：`list_skills` → `load_skill(name)`，按预设技能白名单过滤；技能内容为 Markdown 指令，不进入静态前缀。

**预设解析顺序**：`preset.prompt_extra` 追加至系统提示末尾（标记 `[当前预设：<name>]`）→ 工具白名单裁剪 → 技能白名单过滤 → 模型覆盖（仅本次运行）。

## 七、失效模式与恢复

| 失效 | 检测 | 恢复策略 | 幂等性 |
|---|---|---|---|
| 模型网络错误 / 429 / 5xx | `LlmException.retryable()` | 指数退避重试（500ms → 1s，≤2 次） | 是 |
| 模型 4xx（schema/鉴权） | 状态码判定 | 不重试，转为可读错误 | — |
| 上下文溢出 | 错误文本匹配溢出特征 | 强制压缩一次并重试 | 是 |
| 工具执行异常 | 异常捕获 | 回注 `ERROR: ...`，模型自行调整 | 是 |
| 数据源不可用 | `FetchResult.error/gap` | 降级到备用源 → 缓存 → 标记 `data_status=error` | 是 |
| 三源皆无企业 | 采集后无任何记录 | 撤销建档并返回明确错误 | 是 |
| 审批超时 | `Event.wait` 超时 | 视为拒绝，回注结果继续对话 | 是 |
| MCP 服务不可达 | 初始化/同步异常 | 跳过该服务，不影响内置工具 | 是 |
| 端口冲突 | `listen(0)` 动态分配 | 天然规避 | 是 |
| 后端异常退出 | `child.on('exit')` | 弹窗提示 + 日志路径 | — |

## 八、取舍与边界

### 8.1 复杂度预算

明确拒绝的方案及其理由：

- **多 Agent 编排**（Planner/Executor 分离）：单 Agent + 工具已覆盖当前场景，多 Agent 引入难以调试的状态同步；
- **消息队列/微服务**（Celery/Kafka）：数据量在十万条以内，单机 APScheduler 与同步管道足够；
- **图数据库**：企业关系规模有限，关系表加简单关联即可；
- **向量记忆库**：事实规模用关系查询与会话窗口即可，检索收益不足以覆盖运维成本。

每一项新增基础设施都必须回答"它替代了什么不可替代的复杂度"。

### 8.2 已知限制

1. 样例数据为公开信源整理，财务数字为演示口径，不构成投资依据；
2. 免费数据源存在偶发不可用（实测 1/5），系统以重试、降级与状态标注应对；
3. 模型可能产生幻觉，以规则交叉校验、证据引用与置信度标注降低影响，不能消除；
4. 无用户体系与多租户隔离，面向单机与内网测试；
5. 未做代码签名，Windows 首次运行触发 SmartScreen 提示；
6. 移动端尚未实现。

### 8.3 不适用场景

- 强合规审计环境（需完整操作日志、权限分级与留存策略）；
- 大规模并发服务（需多租户隔离与横向扩展）；
- 实时高频决策（需毫秒级响应）；
- 数据主权敏感场景（依赖外部公开数据源与第三方模型 API）。

## 九、结语

本系统的设计可以概括为一句话：**在不可完全信任的数据与模型之上，构建一个诚实、可追溯、成本可控的风险判断系统。**

由此展开的每一条原则都可追溯到明确的约束与可验证的机制：因为模型不可完全信任，所以工具是唯一入口、写操作必须授权、结论必须附证据；因为数据不可穷尽，所以"缺失"必须是一等状态；因为成本不可无限供给，所以前缀必须稳定、上下文必须稀缺、能力必须按需加载；因为交付环境不可假设，所以系统必须单机可运行。

系统仍有不足：数据源可以更丰富，评测集需要更系统，鉴权与审计需要补齐，移动端尚未开始。但基础是诚实的——它不假装数据完整，不在无法保证精确的地方承诺精确，不在预算允许之外挥霍上下文。它在给定约束下提供可达到的最佳判断，并清晰标注边界。
