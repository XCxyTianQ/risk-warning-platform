# 成本优化：对话压缩与缓存命中

> 目标：让长对话的账单可控。参考 DeepSeek Harness 的 compaction 与 KV Cache 复用设计，
> 在 `server/app/agent/context.py` + `session.py` + `llm/client.py` 落地。

## 1. 为什么缓存命中是成本大头

OpenAI 兼容提供方（含 DeepSeek）按**请求 token 序列的前缀**做 KV Cache：
- 前缀一致 → 命中部分按**缓存价**计费（我们配置里默认 ¥0.5/M，未命中 ¥4/M，输出 ¥12/M）
- 前缀第一个 token 不同 → 整个缓存失效，全部按未命中计费

所以三条硬性约束：

| 约束 | 我们的做法 |
|---|---|
| system 提示词必须稳定 | `agent/prompt.py` 里只有静态角色/规则，**不含时间戳、企业名等易变内容** |
| 工具 schema 必须稳定 | 工具注册表启动时构建一次，顺序固定 |
| 历史必须**追加式** | 消息只 append 不改写；唯一例外是压缩（锚定在头部） |

## 2. 对话压缩（compaction）

### 策略（对齐 DSH `2026-07-20-routed-model-context-and-compaction-policy`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `LLM_CONTEXT_WINDOW` | 128000 | 模型上下文窗口（token） |
| `COMPACTION_THRESHOLD_RATIO` | 0.8 | 估算用量 ≥ 窗口×比例时触发 |
| `COMPACTION_RETAIN_RATIO` | 0.16 | 压缩后保留最近的比例（token 预算） |
| `COMPACTION_SUMMARY_MAX_TOKENS` | 1024 | 摘要输出上限 |

触发点：
1. **主动压力检查**——每次 LLM 调用前重新估算（`context.should_compact`）
2. **溢出恢复**——提供方报上下文超限时强制压缩一次并重试（`context.is_overflow_error`）

折叠规则：
- 从最旧消息起折叠，直到剩余历史 ≤ retain 预算
- **不切断 `assistant(tool_calls)` 与 `tool` 结果**（保持配对完整）
- 摘要写入 `chat_session.summary`，`compacted_until` 记录折叠到的消息 id
- 之后 `store.context()` 返回：`[system 摘要] + 压缩点之后的最近消息` → **上下文体积恒定**

### ★ 关键：摘要调用必须复用已预热前缀（对齐 DSH `2026-07-21`）

错误做法（会让缓存全失效）：
```
[摘要器 system 提示词] + [拍平的历史文本]      ← 第一个 token 就与对话请求不同
```

我们的做法：
```
[对话的 system 提示词] + [对话历史（与最近一次请求字节一致）] + [尾部 user 压缩指令]
                                    ↑ 连 tools 也一起带上，保持 token 序列对齐
```
压缩指令放在**末尾**（`COMPACTION_INSTRUCTION`），因此这次调用是"已预热请求的前缀扩展"，
提供方可以复用已缓存的 token。

## 3. 用量与成本可视化

`llm/client.py` 捕获完整 usage：
```python
{"prompt_tokens", "completion_tokens", "cache_hit_tokens", "cache_miss_tokens", "reasoning_tokens"}
```
流式请求带 `stream_options={"include_usage": true}`，最后一个 chunk 也会返回 usage。

`session.py` 按会话累计并估算成本：
```python
cost = cache_hit/1e6*price_cache_hit + cache_miss/1e6*price_cache_miss + output/1e6*price_output
```
前端对话面板顶部实时显示：**缓存命中率 · 累计 token · 估算成本 · 压缩次数**（悬停看明细）。

`web/src/workspace/StatusBar.vue` 固定在窗口底部，任何页面/面板下都可见：

## 4. 实测结果

多轮对话（真实 DeepSeek，`tests/probe_cache.py`）：

| 轮次 | 输入 tok | 缓存命中 | 命中率 | 累计成本 |
|---|---|---|---|---|
| 1 | 7012 | 6400 | 91.3% | ¥0.0128 |
| 2 | 13423 | 12544 | 93.5% | ¥0.0223 |
| 3 | 16972 | 16000 | 94.3% | ¥0.0254 |
| 4 | 20518 | 18048 | 88.0% | ¥0.0354 |

**会话整体命中率 88%，4 轮对话总成本约 ¥0.035**（若全部未命中，同量输入成本约为其 4~6 倍）。

压缩触发实测（把窗口临时压到 3000、阈值 0.5 以加速触发）：
```
第 1 轮 | 压缩 start → skipped（历史不足）
第 2 轮 | 压缩 start → done 折叠 7 条 → 摘要生成
第 4 轮 | 压缩 start → done 折叠 9 条 → 累计压缩 2 次
```
生产默认（128k 窗口 / 0.8 阈值）下，压缩只在超长会话中偶发触发。

## 5. 提示词缓存预热

**问题**：进程启动后 / 新会话的第一个请求，仍需为静态前缀（system + tools ≈ 2k token）全价处理一次。

**做法**（`app/llm/preheat.py`）：用**逐字相同**的 system 与 tools 发一个最小请求（`max_tokens=1`），
把这段前缀提前写进提供方缓存；之后真实请求的前缀部分即按缓存价计费。

| 时机 | 说明 |
|---|---|
| 服务启动 | lifespan 里后台线程预热（不阻塞启动） |
| 新会话首个请求 | 进入 `/api/chat/stream` 时预热（TTL 内跳过） |
| 压缩完成后 | 前缀变了（system + 摘要）→ 强制预热一次 |

配置：
```env
PREHEAT_ENABLED=true
PREHEAT_ON_STARTUP=true
PREHEAT_TTL_SECONDS=600     # 缓存新鲜期，期内不重复预热
```
本地 mock 端点自动跳过预热。

**实测**（`tests/probe_preheat.py`）：
```
启动预热：warm_count=1, label=startup, 预热时命中 2048 tok, 成本 ¥0.001096
新会话首个请求：输入 2063 tok | 命中 2048 | 未命中 15 | 命中率 99.3%
```
对照（不带 tools 的请求 642 tok）：tools schema 约 1400 token，同样被预热并命中。
状态栏显示 `🔥 预热 就绪 8s`（悬停看预热次数/成本/新鲜期）。

## 6. 可调参数速查

```env
LLM_CONTEXT_WINDOW=128000
COMPACTION_ENABLED=true
COMPACTION_THRESHOLD_RATIO=0.8
COMPACTION_RETAIN_RATIO=0.16
PRICE_CACHE_HIT=0.5     # 元 / 百万 token
PRICE_CACHE_MISS=4.0
PRICE_OUTPUT=12.0
```

> 提示：把 `COMPACTION_THRESHOLD_RATIO` 调低会频繁压缩（省 token 但多一次摘要调用）；
> 调高则更依赖缓存命中。默认 0.8 是 DSH 的取值。
